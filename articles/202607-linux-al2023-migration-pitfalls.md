## はじめに

Amazon Linux 2 (AL2) のサポート終了に伴い、nginx + vsftpd で静的サイトを配信しているEC2を Amazon Linux 2023 (AL2023) へ移行しました。移行の全体的な流れは「[【Amazon Linux 2023】nginx+vsftpd構成の静的配信EC2（AL2）からの新規移行記録](https://zenn.dev/vspgkyo11/articles/202607-linux-al2023-migration)」にまとめています。

流れそのものは「新しく立てて、設定とデータを移して、切り替える」だけなのですが、実際に手を動かすと、旧サーバーの設定をそのまま移しても動かない場面が何度もありました。特にvsftpd周りは日本語の情報が少なく、原因にたどり着くまでに時間を取られました。

本記事では、そのときに踏んだ5つをまとめます。

| # | 落とし穴 | 症状 |
| --- | --- | --- |
| 1 | vsftpdのtcp_wrappersが非対応 | 設定を移植するとvsftpdが起動しない |
| 2 | PASVの `pasv_address` | ログインはできるのに転送だけ失敗する |
| 3 | releaseverが未固定 | サーバーごとにパッケージのバージョンが揃わない |
| 4 | FTPユーザーのnologinシェル | FTPログインが弾かれる |
| 5 | SELinuxのモード | Permissive維持かEnforcing化かの判断 |

## 対象者

* AL2からAL2023への移行を、実際に手を動かして進めているインフラ担当者
* EC2上でvsftpdによるFTPサーバーを運用しているエンジニア
* 移行作業で「旧サーバーと同じ設定にしたのに動かない」に当たっている方

## 落とし穴1: vsftpdのtcp_wrappersがAL2023では使えない

tcp_wrappersは、`/etc/hosts.allow` と `/etc/hosts.deny` に接続元を書くだけで、アプリケーション側の設定を触らずにアクセス制限をかけられる、Linuxで古くから使われてきた仕組みです。AL2のvsftpdでは `tcp_wrappers=YES` を書くことで、これと連携できていました。

ところが、この行を含む設定をAL2023へ移植すると、vsftpdが起動しなくなります。

```
OOPS: tcp_wrappers is set to YES but no tcp wrapper support compiled in
```

AL2023のvsftpdパッケージが、tcp_wrappersのサポートを含まない状態でビルドされているためです。この件は [amazon-linux-2023 のGitHub Issue](https://github.com/amazonlinux/amazon-linux-2023/issues/463) として報告されていますが、2026年7月時点でopenのままです。

:::message alert
設定が黙って無視されるのではなく、起動時にエラーで落ちます。移植後にvsftpdが起動しない場合は、まずこの行を疑ってください。
:::

対処はシンプルで、`tcp_wrappers=YES` の行を移植しないことです。そのうえで、旧サーバーがhosts.allow / hosts.denyで実際にどんな制限をかけていたかを確認し、必要なら同等のルールをセキュリティグループ側に用意します。

なお今回のケースでは、旧サーバーのhosts.allow / hosts.denyは両方とも空でした。つまり `tcp_wrappers=YES` と書いてあるだけで実際には何も制限しておらず、接続元の制限はセキュリティグループ側で完結していた形です。移植前に旧サーバーの実効状態を確認しておくと、こうした「書いてあるが効いていない設定」を新環境へ持ち込まずに済みます。

## 落とし穴2: Elastic IPを使わない構成での `pasv_address`

FTPには、データ転送用のコネクションをサーバー側から張る「アクティブモード」と、クライアント側から張る「パッシブモード (PASV)」があります。クライアントがファイアウォールの内側にいることが多いため、通常はPASVが使われます。

PASVでは、クライアントがファイルを要求すると、サーバーが「このIPのこのポートに繋いでください」と応答し、クライアントがそこへデータ用の接続を張ります。このときサーバーが応答するIPが `pasv_address` です。

厄介なのは、EC2は自分のグローバルIPを知らないという点です。サーバー自身から見えるのはプライベートIPだけなので、`pasv_address` にはグローバルIPを手動で書く必要があります。

今回はコスト面からElastic IPを付けず、AWSが自動で割り当てるパブリックIPを使う構成にしました。この場合、インスタンスを停止・起動するとIPが変わります。`pasv_address` に古いIPが残っていると、次のような症状になります。

* FTPログインはできる（制御用の接続は成立している）
* ファイル一覧の取得や転送だけがタイムアウトする（データ用の接続が、もう存在しないIPへ向かっている）

:::message
「ログインはできるのに転送だけ失敗する」はPASVの典型的な症状です。`pasv_address` の値と、パッシブポートの開放状況をまず確認するとよいです。
:::

あわせて、パッシブ接続に使うポート範囲 (`pasv_min_port` / `pasv_max_port`) が、セキュリティグループの受信ルールで開放されているかも確認が必要です。FTPは制御用の21番だけ開けても動きません。

対処の方向性は2つあります。

* **Elastic IPを割り当てる**: `pasv_address` に固定のグローバルIPを書いて終わり。以後は考えなくてよい
* **自動割り当てIPのまま運用する**: 停止・起動のたびに `pasv_address` を見直す運用ルールを決めるか、起動時にパブリックIPを取得して設定へ反映する仕組みを用意する

今回は既存構成を踏襲して後者にしましたが、正直なところ、グローバルIPが変わった瞬間に転送が壊れる構成を運用でカバーし続けるのは分が悪いと感じました。FTPサーバーに関しては、多少のコストを払ってでもElastic IPを割り当てておくほうが安全だと思います。

## 落とし穴3: releaseverを固定しないとサーバーごとにバージョンが揃わない

dnfはAL2023のパッケージ管理コマンドで、AL2の `yum` にあたるものです。AL2023では、このdnfが参照するリポジトリが日付入りのリリース番号 (releasever) で管理されており、`/etc/dnf/vars/releasever` に値を書くことで、参照先を特定時点のスナップショットに固定できます。AWS公式が「[Deterministic upgrades](https://docs.aws.amazon.com/linux/al2023/ug/deterministic-upgrades-usage.html)」として案内している仕組みです。

これを固定せずに複数台を別々のタイミングで構築すると、使ったAMIの世代や `dnf update` を実行した日によって、サーバーごとに微妙に違うパッケージが入ります。障害調査のときに「A号機では再現するがB号機では再現しない」という、本題と関係のない変数が増えることになります。

今回は新サーバーを複数台構築する計画だったため、事前に決めたリリース番号を全台で固定しました。

```bash
# 現在参照しているリリース番号を確認
cat /etc/dnf/vars/releasever

# 全台で共通のリリース番号に固定する
echo "2023.12.xxxxxxxx" | sudo tee /etc/dnf/vars/releasever

sudo dnf clean all
sudo dnf update -y
```

固定値を決めておけば、後から増設するサーバーも同じバージョンで揃えられます。

:::message alert
固定したまま放置すると、その時点以降のセキュリティパッチが当たりません。固定値を見直すタイミングを、あらかじめ運用ルールに組み込んでおく必要があります。
:::

## 落とし穴4: FTPユーザーをnologinにするとログインできなくなる

FTPでしか使わないユーザーには、シェルログインをさせない意図で `/sbin/nologin` を割り当てるのがセキュリティ上の定石です。今回もその方針でFTP専用ユーザーのシェルをnologinにしたところ、vsftpdへのログイン自体が拒否されるようになりました。

原因はPAM (Pluggable Authentication Modules) にあります。PAMはログイン認証の処理を部品として差し替えられるようにしたLinuxの共通基盤で、vsftpdもこれを使って認証しています。

vsftpdのPAM設定 (`/etc/pam.d/vsftpd`) には `pam_shells.so` という部品が含まれており、これが「ユーザーのログインシェルが `/etc/shells` に載っているか」を検証します。`/etc/shells` には通常 `/bin/bash` などの対話用シェルしか登録されておらず、`/sbin/nologin` は含まれません。結果として、nologinのユーザーはFTPログインの時点で弾かれます。

これはAL2023固有の問題ではなく、RHEL系ディストリビューション全般で知られている挙動です。ただ、移行を機に「せっかくだからnologinにしておこう」と設定を締めた結果として踏むことが多く、旧環境から変えた箇所だけに原因の切り分けがしにくい落とし穴です。

対処の選択肢は3つあります。

* `/etc/shells` に `/sbin/nologin` を追記する。手軽だが、シェルの許可リストという仕組み自体を骨抜きにするので推奨しない
* FTPユーザーのシェルは対話用のまま残し、SSH側を別の手段（鍵を配らない、パスワード認証を無効化する等）で塞ぐ
* システムユーザーと切り離した仮想ユーザー (virtual user) 方式へ移行し、OSのログインシェルという概念から切り離す

今回は既存構成を踏襲する必要があったため2つ目を選びましたが、恒久的には仮想ユーザー方式が本筋だと考えています。

## 落とし穴5: SELinuxをPermissiveのままにするか、Enforcing化するか

これだけは「踏んだ」というより「判断を迫られた」という話です。

SELinuxは、通常のファイル権限とは別の軸で、どのプロセスがどのファイルやポートにアクセスできるかを制御するLinuxのセキュリティ機構です。旧サーバーではSELinuxが無効化されていましたが、AL2023のデフォルトはPermissiveモードです。

Permissiveでは、ポリシー違反 (AVC拒否) が起きてもアクセスはブロックされず、ログにだけ記録されます。つまり、Enforcingへ切り替える前に「切り替えたら何がブロックされるか」を、実害なく観察できる状態にあるということです。

観察と切り替えの一般的な手順は次のとおりです。

```bash
# 直近のAVC拒否ログを確認する
sudo ausearch -m avc -ts recent

# 記録された拒否ログから、許可すべきポリシーモジュールを生成する
sudo ausearch -m avc -ts recent | audit2allow -M mypolicy

# 生成したポリシーを適用してから Enforcing へ切り替える
sudo semodule -i mypolicy.pp
sudo setenforce 1
```

Enforcing化に踏み切るかどうかは、次のあたりが判断材料になります。

* セキュリティ要件やコンプライアンス上、Enforcingが求められているか
* AVC拒否ログを十分な期間観察でき、業務影響のあるアクセスを誤ってブロックしない確信が持てるか
* 切り替え後に問題が起きたとき、切り戻しと調査ができる体制があるか

今回は、長年SELinux無効で安定稼働してきたサーバーの引っ越しであること、静的ファイルを配るだけでSELinuxが守る対象が乏しいことから、Enforcing化のメリットより切り替えに伴う障害リスクが上回ると判断し、Permissiveのままとしました。

:::message
今回はPermissiveを維持したため、上記のEnforcing化手順は実際には実行していません。一般的な手順として紹介しています。同様の構成を新規に立てるなら、稼働初期のうちにログを観察しながらEnforcing化を検討する価値はあると思います。
:::

## おわりに

書き出してみて改めて思ったのは、5つのうち4つが「旧サーバーの設定をそのまま持ってきた」ことに起因しているという点でした。移行作業では、現に動いている設定をそのまま移すのが一番安全に思えます。しかし実際には、旧環境ですでに意味を失っていた設定（今回でいえば何も制限していなかったtcp_wrappers）や、環境が変われば前提が崩れる設定（自動割り当てIPと `pasv_address`）が紛れています。

「そのまま移す」は、そのまま移してよいかを一行ずつ確認して初めて成立するのだと、今回の作業で実感しました。移行前に旧サーバーの実効状態を確認しておくのが、遠回りに見えて一番の近道だと思います。

AL2のEOL対応で同じ構成に当たっている方の、時間の節約になれば幸いです。
